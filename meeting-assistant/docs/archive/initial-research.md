# Local Teams meeting transcription, translation, notes and vocabulary

> Historical research snapshot. See the [current plan](../plan.md) and [selected-model verification](../selected-model-research.md) for subsequent user decisions. Local-only post-processing and earlier model recommendations below are superseded.

**Research date / sources accessed:** 2026-11-09. **Target:** personal MacBook Pro, base Apple M5, 10 CPU cores, 24 GiB unified memory, 1 TB storage, macOS 26.7.1, verified by parent session; meetings up to **two hours with 5–15 participants**; an intermediate Mandarin learner. Taiwanese Mandarin mixed with English; Traditional Chinese source and timely English **text captions only**, with no speech synthesis or TTS. Automatic Teams participant names are preferred; anonymous speaker labels and manual mapping are acceptable. Use local Teams audio, no bot or cloud requirement, and strictly local processing by default. This is a source-based assessment, **not a benchmark or an implementation test on this Mac**. References link directly to model owners, runtime maintainers, app authors, Apple, Microsoft, or dictionary maintainers. Repository pages can change; pin commits and model revisions for any build.

## Executive recommendation

1. **Updated user constraint:** built-in Teams translation is not available to this user, and **Teams Mac desktop only** is required. Time-box an authorized check of whether the visible live transcript is exposed through macOS Accessibility; otherwise proceed with local audio ASR. A supported Work IQ feed is optional only if already authorized and practically available, not a prerequisite. Do not depend on a browser extension. As optional build-versus-buy baselines, [Meetily](https://github.com/Zackriya-Solutions/meetily) offers capture, real-time transcription and local summary, and [Vibe](https://github.com/thewh1teagle/vibe) local audio transcription and English translation. Neither app source establishes the entire required live bilingual pipeline or the Taiwanese vocabulary output. Use a consented sample and verify all configured providers are local.
2. **Build candidate A, practical local baseline:** capture remote output and microphone as separate tracks → VAD and bounded overlapping chunks → **Whisper large-v3-turbo with whisper.cpp/Metal** → preserve raw transcript; convert Chinese display to Taiwan Traditional → local text translator. Start by evaluating **Qwen3.5-4B quantized in non-thinking mode** for an Apache-licensed general-purpose path; compare HY-MT1.5-1.8B standard GGUF **only if its territory-limited license permits use**, and test Hy-MT2-1.8B Q4 as a challenger **only after its exact runtime and Metal compatibility gate below passes**. None has been benchmarked here. English already spoken should pass through; mixed sentences should retain English terms. Validate fragmented input, omissions and latency.
3. **Challenger B, native streaming—not a two-hour turnkey solution:** **VibeVoice-ASR-Streaming-1.5B on MLX** → same translation stage. Microsoft states the released streaming checkpoints support **at most eight minutes per recording**; retained history grows with length. For two hours reset at or before that limit, carry audio across boundaries and reconcile speaker IDs separately. The published card/report does not establish a 15-participant capacity; do not assume one. Its MLX implementation documents live-buffer state but is a separate port, not a two-hour M5 validation. Compare its approximately 2.933 s new-audio chunk plus 0.533 s lookahead and total parameter footprint against accuracy and comfort; these are implementation characteristics, not measured M5 latency. Speaker labels are opportunistic, never on the critical path. [Microsoft report, §§3.1, 4, 6](https://arxiv.org/html/2609.02812v2), [MLX implementation](https://github.com/Blaizzy/mlx-audio/blob/main/mlx_audio/stt/models/vibevoice_asr/README.md).
4. **Quality-oriented challenger:** Qwen3-ASR-1.7B using the [MLX-Audio implementation](https://github.com/Blaizzy/mlx-audio) with a separately built VAD/window/revision loop, plus a locally verified translator. Qwen's own streaming API is **vLLM-only**, and omits streaming timestamps and batching; do not equate the owner’s streaming claim with turnkey M5 streaming. [Qwen repository](https://github.com/QwenLM/Qwen3-ASR).
5. **After meeting:** save consented audio; re-transcribe with longer context, benchmark **MOSS-Transcribe-Diarize 0.9B** and/or Qwen3-ASR-1.7B and Whisper large-v3; perform offline diarization if needed; review speakers; run a quantized **Qwen3.5-9B** locally in short hierarchical passes with citations back to time-coded evidence. Generate vocabulary with 2B or 4B, but derive and validate pinyin from dictionary-backed tools, not unverified model output.

6. **Names:** investigate a policy-approved, reliable source of time-aligned Teams speaker metadata only as an optional integration. The documented alternatives involve Teams/Microsoft services and permissions, not a proven offline, bot-free macOS mixed-audio metadata feed. Default to anonymous speakers and an editable manual mapping; captions never wait for naming.

**Target, not a prediction:** start with a **2–5 s median** from relevant phrase end to understandable English caption, and measure p95, not just median. Partial captions can appear earlier and must be marked provisional. This target may be missed, especially on uninterrupted speech or with GPU contention; if so prioritize comprehension, suppress backlog, and test alternative chunking/models. Neither any vendor latency claim nor model size establishes M5 performance.

Avoid assuming a cloud provider's similar-sounding text-model alias is this audio model.

### Runtime and streaming reality

- [whisper.cpp](https://github.com/ggml-org/whisper.cpp) runs Metal; it also documents a Core ML encoder path and VAD. [Apple MLX Whisper](https://github.com/ml-explore/mlx-examples/tree/main/whisper) is another Apple-native option. Compare **same checkpoint, quantization and decoding settings**.
- [faster-whisper](https://github.com/SYSTRAN/faster-whisper) uses CTranslate2; its documented GPU path requires NVIDIA CUDA/cuBLAS/cuDNN. On this Mac, treat it as CPU inference, **not Metal acceleration**. Its NVIDIA and Intel speed figures cannot be ported to M5.
- [Whisper-Streaming](https://github.com/ufal/whisper_streaming) documents an MLX backend and LocalAgreement, where repeated overlapping decodes commit a shared prefix. Its maintainers recommend its successor [SimulStreaming](https://github.com/ufal/SimulStreaming), which adds AlignAtt and supports Whisper speech-to-English or a translation cascade. However, the documented SimulStreaming Whisper backend uses PyTorch and recommends a GPU with 10 GB VRAM; its CPU warning and examples do **not** establish fast Metal deployment. Older wrapper's MLX support does not automatically transfer to successor. For either, account for repeated decoding, revisions and mixed-script chunk stitching.
- [SeamlessStreaming](https://github.com/facebookresearch/seamless_communication) is a genuinely streaming 2.5B speech-to-text/speech-to-speech candidate with Mandarin support. Its owner distributes weights under **CC-BY-NC-4.0**, separately from MIT code; its dependencies include fairseq2, whose stated prebuilt targets include Apple Silicon, but no M5 real-time guarantee. `unity.cpp` in that repo is for **SeamlessM4T**, not proof that SeamlessStreaming is supported on Metal. It provides an experimental direct-S2T comparison, not the default business workflow, and source transcript plus translation still need evaluation.

Translation should use stable source clauses plus a small, clearly delimited preceding context and an optional approved domain glossary. Prompt: “Translate only the current text to English; retain existing English names and acronyms; do not invent omitted subjects, decisions or deadlines; output only translation.” Compare raw Mandarin to translation, not polished English alone. ### Hy-MT2 Q4 / Metal compatibility gate (verified 2026-11-09)

- Tencent's [standard Q4/Q6/Q8 repository card](https://huggingface.co/tencent/Hy-MT2-1.8B-GGUF) says **“This gguf depends on our STQ kernel” without restricting the warning to 1.25-bit**, and its example uses `-ngl 0`. The Hugging Face page also presents automatically generated llama.cpp/Q4 launch instructions; those are **not evidence of a successful Metal run**.
- [PR #22836](https://github.com/ggml-org/llama.cpp/pull/22836) was **open and unmerged** when checked; it adds `STQ1_0` ternary quantization and an ARM NEON CPU kernel. Its own example and M4 Pro measurements use `-ngl 0`. Its [changed-file list](https://api.github.com/repos/ggml-org/llama.cpp/pulls/22836/files?per_page=100) does not establish an STQ Metal kernel. This does **not** prove the separate standard Q4 file necessarily contains STQ tensors; the card and PR alone do not resolve the conflict.
- The GGUF listing identifies [Q4_K_M](https://huggingface.co/tencent/Hy-MT2-1.8B-GGUF/blob/main/Hy-MT2-1.8B-Q4_K_M.gguf) as a specific 1,133,080,448-byte artifact, SHA-256 `dc5f44fcf1fa496ee7ad725982c0c8c553a4de00259b53af84c4b89fb0c06699`; the hub reports `hunyuan-dense` architecture and llama.cpp [registers that architecture](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-arch.cpp) with a [model implementation](https://github.com/ggml-org/llama.cpp/blob/master/src/models/hunyuan-dense.cpp). Its [Metal backend source](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.cpp) includes `GGML_TYPE_Q4_K` in a matrix-vector kernel dispatch. Architecture registration and generic Q4 support do not prove the exact artifact has no STQ tensors, that all its operators offload, or that it runs correctly with Metal.
- **Acceptance gate:** download the exact pinned file after approval, verify hash and inspect GGUF tensor types using a trusted parser; pin a llama.cpp build, load with logs, confirm which layers/operations are actually offloaded to Metal and whether any fall back to CPU; compare output against a CPU reference on Mandarin/English test phrases; measure warm latency and memory while live ASR and Teams run. Include 2-hour stability. No such runtime test was performed here. If loading, quality, performance or license review fails, select Qwen3.5-4B local, or HY-MT1.5 only where its license permits and it passes equivalent testing. Re-check the open PR and model card before deployment.

**Optional remote services:** Only if a local approach proves insufficient and the user explicitly opts in, the already-used API gateway may be considered with the supplied `deepseek-flash-gmi` / `deepseek-v4.1-flash-1017` or `nemotron-3.5-lightning-30b-a3b-spc` aliases. These are user-provided provider aliases; public model names do not verify their availability, mapping, free quotas, retention, or equivalence. No endpoint or credentials are inferred, and no gateway API was invoked. Any such use is **cloud processing**, not offline. Only send explicitly approved, consented and minimized text after reviewing provider/company terms, residency, retention and credentials. Keep a clear local-only mode with no automatic fallback.

## Capture, privacy and Traditional Chinese

Apple’s [Screen & System Audio Recording privacy settings](https://support.apple.com/guide/mac-help/control-access-screen-system-audio-recording-mchld6aa7d23/mac) cover app access to screen and system audio; [ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit) is Apple's capture framework. Microphone requires its separate privacy authorization. OS version, managed-device policy, Teams audio routing, headphones, Bluetooth and permission behavior must be tested. A virtual audio device is a fallback, not an assumed requirement.

Capture **remote/system output** and **local microphone** separately with a common monotonic clock; preserve originals and timestamps, normalize to a common sample rate for inference, and consider clock drift. Do not assume remote Teams participants are separately available: system playback is usually a mixed remote track, so it does not contain a reliable person-to-channel mapping. Local mic can contain remote speaker echo; headphones or echo cancellation help, but suppression can erase quiet speech. Detect clipping, missing channels and track changes. Preserve overlapping audio; a mixed track can hide simultaneous words.

Use [OpenCC](https://github.com/BYVoid/OpenCC) for deterministic conversion: `s2tw` for Simplified → Taiwan Traditional, `t2tw` where appropriate for already Traditional; `s2twp` additionally changes regional phrases. Prefer conservative **script/character conversion** for the verbatim transcript. Phrase localization such as 鼠標 → 滑鼠 changes wording; apply separately as a labeled display option and retain raw ASR, source offsets and audit trail. Do not run blind conversions over proper names/code identifiers. A text converter neither recognizes a Taiwanese accent nor translates Taiwanese Hokkien; Mandarin accent, Hokkien speech, orthography and regional vocabulary are distinct. Use approved TW domain terminology/glossary and allow human corrections.

### Alternative input: Teams transcript or built-in translated captions

Before building a live captioner, check [Teams' translated live captions](https://support.microsoft.com/en-us/teams/meetings/use-live-captions-in-microsoft-teams-meetings): Microsoft lists Traditional Chinese (Taiwan) and English and specifies eligible Premium/Copilot licensing and policy requirements. Test the actual meeting's spoken-language and caption-language controls, code-switching, speaker names and latency; eligibility is not assumed. This convenient route uses Teams transcription/translation services, **not fully on-device inference**.

For a hybrid design, use an **approved, supported live text feed**, if actually available, as an input adapter to a local translator; preserve speaker labels, timestamps, revisions, language and provenance, then display provisional and finalized English text. Microsoft documents [Work IQ real-time transcripts with speaker names](https://learn.microsoft.com/en-us/microsoftteams/meeting-transcript-api-access), subject to a signed-in user, app permissions, active transcription, AI allowed and Work IQ enabled. The independent setting's enforcement date is **2026-11-14**, not the service's launch date; this report is as of November 9. Microsoft's [tenant-enablement guide](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/work-iq/enable-work-iq) also lists a usage-based billing plan and administrator setup, so do not assume this is a free, immediately available personal integration. A working raw transcript consumer, delivery semantics, latency, terms and actual costs still need proof. This is a networked Teams source and requires authorization, so it is an optional hybrid rather than the offline default. The documented [standard Graph transcript workflow](https://learn.microsoft.com/en-us/microsoftteams/platform/graph-api/meeting-transcripts/overview-transcripts) is post-meeting retrieval; do **not** assume polling it yields a growing live transcript. If authorized, a user-provided post-meeting VTT import is a simpler batch input for local summaries and vocabulary, but does not provide live translation.

Reading visibly displayed captions through a browser's DOM or macOS accessibility may be technically investigable, but availability, reliability, stability, meeting policy and permissions are unverified. It is an experimental, user-authorized display adapter only: **no private endpoint, protected-content bypass, hidden scraping or evasion of controls**. If access is unavailable or disallowed, use the on-device audio pipeline; do not silently fall back to a cloud service.

All participants should receive clear notice and any legally and organizationally required consent **before capture or recording**. Check local law, corporate policy and meeting host rules. Keep audio/transcripts encrypted at rest where available, use local access controls, visible recording state, per-meeting retention/deletion and explicit export. Do not store voiceprints by default. Pre-download pinned assets, test with networking disabled, disable telemetry/automatic updates as applicable, restrict local server to loopback, and verify no unexpected network egress; a local model download is not offline until assets are cached.

**Speaker A ≠ Alice.** Clustering is “who spoke when,” not a Teams identity system. Names from a roster cannot be matched by voice alone. If available, user manually labels a short verified sample or uses separately consented enrollment; keep `unknown`, corrections and confidence, and never infer a speaker simply from semantic content. Track provenance such as `local mic` versus `remote mixed`; even a local mic might include someone else. A named per-person summary should be generated **only after** a reviewed mapping; otherwise produce anonymous per-speaker notes and mark overlap/uncertain attribution. A larger LLM cannot repair missing speaker identity.

Align clocks, allow many-to-one/unknown and overlapping speakers, and test delayed events, guest and room accounts, participant reconnects and duplicate display names. Do not propagate an uncertain label into a named action item. No Microsoft Graph, Teams, Work IQ, or provider-gateway API was contacted for this research.

## Post-meeting pipeline and summaries

1. Persist timestamped track metadata and raw, immutable ASR hypotheses; run a second pass on original audio in bounded overlapping windows with enough context. Compare Qwen3-ASR-1.7B, MOSS 0.9B, and Whisper large-v3 on the same meeting slices. Use the best validated method, not majority vote as a ground truth. Flag cross-model disagreement, low-quality or inaudible spans. Use [Qwen3-ForcedAligner](https://github.com/QwenLM/Qwen3-ASR) or another validated aligner after selecting transcript; it aligns provided text and **cannot prove the text was spoken**. Retain original time offsets.
2. Merge each transcript span with diarization timeline. Keep overlap and ambiguous attribution; run explicit review for identities and commitments. Source spans contain `id`, start/end, track, speaker cluster, raw text, normalized text, confidence/review status and model/version.
3. Chunk long meetings by coherent boundaries with overlap. For each chunk, generate structured claims with one or more **exact transcript span IDs, timestamps, verbatim quotation, speaker/unknown**, plus topic and tentative status. Preserve negations, alternatives, uncertainty and counterevidence. Deduplicate and consolidate evidence into final overall summary, decisions, open questions, and per-speaker contributions. A second source-validation pass checks each claim against the cited transcript and audio when consequential; reject unsupported items. References remain clickable to original text/audio.
4. Action item schema: `action`, `owner` (unknown allowed), `deadline` (only if explicitly stated; otherwise null), `status` (proposal vs accepted commitment), `evidence_span_ids`, `quote`, `speaker_mapping_status`. A speaker asking a question or merely describing a plan is not automatically committing to do it. Human approval before sharing.
5. Run **Qwen3.5-9B quantized locally** after unloading live ASR/MT when feasible. Use smaller 4B if memory/speed dictates; do not assume the official huge context fits. Reduce hierarchically instead of dumping a whole meeting into one enormous prompt. Evaluate factuality and omissions regardless of size.

**Two-hour speaker reconciliation:** use a full-recording, variable-speaker offline diarizer as one baseline, subject to measured 24 GiB feasibility; do not force 15 if fewer actually speak. With chunked MOSS, output IDs are local to each chunk. Preserve absolute timestamps, overlap boundaries and `(chunk, local speaker)` provenance; compare overlap segments and, where speech is sufficient, consented local speaker embeddings across the full recording. Cluster cautiously, review short utterances, returning speakers, similar voices and simultaneous speech; permit unresolved labels and later split/merge corrections. Resetting VibeVoice at ≤8 minutes likewise resets its model context and labels; do not assume its `Speaker 1` survives a reset. Avoid irreversible automatic identity merges, and re-run affected summaries after corrections. Protect/delete voice embeddings with the audio; they are sensitive voice-derived data and do not establish a person's identity.

## Traditional Chinese vocabulary and pinyin

**Is Qwen3.5 2B enough?** It may be sufficient to propose candidate terms and short contextual glosses from small transcript chunks, but this is an unmeasured hypothesis, not a quality guarantee. Compare 2B versus 4B/9B on a labeled sample, and validate every candidate by exact occurrence in transcript; use 9B for difficult semantic distinctions when available. It should not invent source quotes, timestamps, names or pinyin. Separate candidate discovery, ranking, dictionary lookup and review.

1. Extract candidate Chinese words/phrases from source spans with speaker/time evidence; normalize display to Traditional without erasing raw spoken text. Segment language-aware; preserve English terms, project names, abbreviations and phrases (not just individual characters). Map simplified and variant spellings while storing originals.
2. For this **intermediate learner**, rank by learner usefulness, unknown-to-user terms, TW workplace/domain phrases, collocations, natural meeting expressions and illustrative context; frequency is one signal, not the sole objective. Provide concise contextual glosses and optionally example usage, avoiding elementary words unless a nuanced meeting sense matters. Allow known-word marking and an editable list. Exclude filler and common known words unless important. Distinguish literal translation from the meaning used here.
3. Query [CC-CEDICT](https://cc-cedict.org/wiki/) locally for Traditional headword, sense and numbered pinyin; its **CC BY-SA 4.0** data require attribution and potentially share-alike obligations for adapted distributions. [pypinyin](https://github.com/mozillazg/python-pinyin) is MIT-licensed code with phrase-aware and heteronym modes, traditional support and tone styles; check bundled/extra dictionary data licenses separately. Dictionary/phrase-level lookup is preferred; context plus segmentation decides heteronyms. Preserve alternatives and uncertainty when ambiguous; CC-CEDICT and pypinyin may prefer mainland pronunciation, so consult a licensed Taiwan reference or human for TW variants. Define lexical citation tones vs optional spoken tone-sandhi. For example `銀行` = **yínháng / yin2 hang2**, whereas `行動` = **xíngdòng / xing2 dong4**; do not pick a character's first pronunciation blindly. Names and out-of-vocabulary phrases need manual review.

Illustrative **fabricated** row, not a real meeting excerpt:

| Traditional term | Pinyin marks / numbers | Meaning in this context | Exact source quote + time / speaker | Rank reason | Validation |
|---|---|---|---|---|---|
| 進度 | jìndù / jin4 du4 | progress | `目前進度如何？` · 00:12:10 · Speaker B (unverified) | reusable meeting phrase | transcript exact-match; dictionary headword/reading; human review |

Store entry ID/dictionary version, raw source, quote offsets, meaning, alternate readings, known-word status and evidence confidence. Reject a vocabulary row without real source evidence; do not export the example as observed speech.

## Memory, responsiveness and reliability budget

**All numbers below are planning ranges, not measured M5 allocations or guaranteed fit.** 24 GB is shared by OS, Teams, browser, CPU/GPU/ANE work and page cache. Model parameter count is not runtime resident memory: weights + unquantized components + KV/state + activations + audio buffers + framework/Metal workspaces + fragmentation and macOS memory pressure matter. The [Whisper.cpp table](https://github.com/ggml-org/whisper.cpp) reports large model ~3.9 GB memory in its generic setup, not an M5/Teams benchmark; Tencent's Q4 1.13 GB is **disk file size**, not total memory.

| Planning component | Rough allowance | Notes |
|---|---:|---|
| macOS + Teams + browser | 6–10 GB | Widely variable; screen sharing and other applications increase it. |
| Live ASR process | 2–5 GB | Turbo or Qwen quantized; VibeVoice upstream BF16 files alone ~5.6 GB, so allow more for that candidate. |
| Live translator | 1.5–4+ GB | Illustrative small quantized translator including runtime and short context; Hy-MT2 Q4 file alone is 1.13 GB. Qwen3.5-4B and actual workspaces may exceed this range; measure. |
| Audio, UI, VAD, workspaces | 1–3 GB | Avoid double-counting shared allocations; grow with buffering. |
| Margin | 3–5+ GB | Avoid sustained pressure/swap; the lower ends sum to ~13.5 GB, higher illustrative ends ~22 GB **before** extra workloads. |

Concurrent model bandwidth/compute contention can cause lag even if allocations fit. Start one ASR and one translator; omit live diarizer and large summarizer. Leave 9B Q4 and diarization for after the call; nominal 9B × 4-bit ≈ 4.5 GB **raw theoretical weights**, not complete file/runtime. At load, try short contexts and no vision encoder if supported; swapping multiple models can exceed headroom. Prefer batch sequential stages and unload rather than running all concurrently.

Design bounded queues and backpressure: schedule ASR first, coalesce updates, cancel obsolete MT jobs, cap pending audio/text, track original offsets, warn explicitly about falling behind. Do not silently drop audio or present lagged captions as live. Disable repeated speculative translation of every token; update on stable phrases. Monitor real memory pressure, swap writes, CPU/GPU/ANE activity, fan/temperature and Teams call quality. Test AC and battery, sustained calls and different output devices.

## Evaluation: acceptance before choosing a winner

1. Obtain consent and create a small **representative** local corpus, e.g. 60–120 minutes across several meetings/speakers, with a locked holdout. Include Taiwanese accents, local terms, internal abbreviations, fast code-switches within one clause, English-only intervals, overlap, headset vs speakers, weak connections, music/noise, silence, multiple people in a room and different speaking rates. Create human timestamped Mandarin Traditional/English references and independent speaker annotations. Include synthetic safety cases with numbers, names, dates, negation and decisions, not confidential recordings without approval.
2. Replay audio at real-time speed while Teams is in a representative call with screen sharing. Use identical inputs, sample rate, segmentation, model settings, warming and quantization; pin app/model/runtime versions. Test both cold and warm start and **at least two hours sustained**, including each eight-minute VibeVoice reset, speaker re-entry and after device changes. Record per-stage and end-to-end timelines including buffering, inference and UI display. Do not use computationally-unaware simulation as observed latency.
3. Report **Mandarin CER** after a fixed Traditional normalization policy and **English WER**, plus mixed error rate with a documented tokenization; evaluate numbers, terminology and code-switch spans separately. Report raw and normalized text separately to avoid hiding conversion mistakes. Manually audit semantic transcription errors, missed short speech and hallucinations per hour of silence/noise.
4. Have bilingual reviewers rate English subtitle adequacy/comprehensibility, omissions, additions, polarity, named entities and commitments, separately on clean source text and ASR output. Score provisional versus final revisions and cutoff sentences; provide examples and confidence intervals. Compare with large-v3 direct speech translation as an independent path, bearing in mind it does not provide source in the same pass.
5. Measure p50/p95 **end-of-phrase to first and stable English**, inter-caption gap, revision rate, queue delay and backlog growth. Record RTF including overlap reprocessing, load time, peak resident/unified memory, swap, power, throttling and call audio quality. Suggested initial gates: most sentences understandable, median 2–5 s and p95 within a user-agreed ceiling, no growing queue across two hours, no material call degradation. These are proposed acceptance criteria, not known capabilities.
6. On human-labeled reference compare diarization DER/JER with stated collar/overlap policy, speaker-attributed CER/cpCER and false real-name attribution. Test representative 5, 10 and 15 participants, including speaker return after absence, chunk/session-boundary identity swaps and actual active-speaker counts; report identity accuracy separately from clustering. Have humans audit summary claim entailment, omissions, false action items, owner/deadline correctness, evidence resolution, and vocabulary exact-match, selected-sense and pinyin accuracy. Treat low-quality data as a reason to abstain.

## Phased implementation

1. **Permissions & baseline:** policy/consent, two-track recording test, Teams routes; run Meetily and Vibe locally; compare outputs against human reference. Record software and data-handling settings.
2. **Live minimum:** whisper.cpp turbo + VAD + conservative Traditional conversion + tested local Qwen3.5-4B or a license-eligible HY-MT1.5 standard GGUF; test Hy-MT2 Q4 only after the compatibility gate. Source and English provisional/final overlay; separate tracks and bounded queues. Establish measurements and fallback if overloaded.
3. **ASR bake-off:** VibeVoice native MLX, Qwen MLX windows, optionally Nemotron 3.5 streaming and SenseVoice/Fun-ASR. Choose by Mandarin/code-switching accuracy *and* measured end-to-end latency, not architecture alone. Tune segment duration, glossary and stable-prefix policy.
4. **Second pass:** reprocess original audio, diarize with MOSS and/or pyannote/FluidAudio, annotate uncertainties, user-review identity, align time spans. Prove offline with network blocked.
5. **Notes and vocabulary:** Qwen3.5 local 9B/4B for grounded chunk-and-reduce summaries; test 2B vs 4B for candidate terms; local dictionary-backed pinyin and human correction; evidence-linked export and deletion.

## Open questions / blockers

- Teams Mac desktop is required and built-in translation is unavailable. Headset/speaker setup, actual memory available during calls and acceptable call/overlay interaction remain to be verified.
- Are notice, recording, local persistence and use of external open weights permitted for each meeting? Required retention/encryption and distribution license policy?
- Is the user mostly listening, or do local microphone and remote speech both need captions? Is a local always-on-top window sufficient? Desired maximum p95 latency and quality/error tolerance?
- Would the organization authorize any optional Microsoft Graph or Work IQ integration, recognizing it is not fully offline? Automatic Teams names are preferred and manual mapping is acceptable; otherwise use anonymous clusters and manual mapping. What proportion of the 5–15 attendees typically speak or overlap?
- Speech is confirmed Mandarin plus English, not a request for Hokkien recognition. Default to conservative Taiwan Traditional display, retaining raw ASR; optional regional phrase localization, approved glossary and excluded sensitive vocabulary need confirmation.
- For the intermediate learner, is there an existing known-word list, preferred vocabulary quantity, tone-mark vs numbered pinyin, desired Taiwan-specific pronunciation and review workflow?
- What jurisdiction applies to the personal Mac and meeting data? HY-MT1.5's bundled license excludes the EU, UK and South Korea, so the fallback cannot be chosen without checking location and terms.
- Can model downloads and gated HF registrations happen in advance? Which exact runtime, conversion, terms and versions are approved? Can the finished solution be reliably tested without network egress?

**Bottom line:** A complete, reliable offline bilingual Teams assistant is plausible but not established by any single model card or app page. The decisive unknowns are capture consent/routing, real code-switch accuracy, streaming implementations on the exact Mac, verified latency under Teams load, and dependable real-person identity mapping.
